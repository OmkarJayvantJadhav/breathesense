# Analysis and decisions (hand-written)

_Based on the measured sections above plus three follow-up probes run on 2026-09-28
(see `data/samples/unit_check_*.json`). Items marked **OWNER DECISION** need approval
because they change a project rule._

## A. Key findings

1. **India filter works on `/locations`, not on `/parameters/{id}/latest`.** `iso=IN` and
   `countries_id=9` return the same 764 locations, all with country code `IN`, in a single page
   (`limit` max is 1000; `limit=1001` → HTTP 422). `/parameters/{id}/latest` ignores both filters
   (21,124 rows worldwide for either filter), so a cheap India-wide "latest by parameter" pull is not possible.
2. **Upstream CPCB outage in progress.** Every CPCB station's newest data is
   **2026-09-24 17:30 UTC** (≈ 90 h before this run), confirmed per sensor via `/locations/{id}/latest`
   and `/sensors/{id}` (not just location metadata). Only AirNow (US Embassy, PM2.5) is live.
   No matching public OpenAQ incident found; related but distinct issues:
   [openaq-ingestor#23](https://github.com/openaq/openaq-ingestor/issues/23),
   [openaq-ingestor#24](https://github.com/openaq/openaq-ingestor/issues/24).
   The benchmark therefore used the last 3 hours before the CPCB feed head. Request cost,
   completeness and duplicates are valid; **arrival latency could not be measured** and must be
   re-measured once the feed resumes.
3. **CPCB native resolution is 15 minutes.** `/sensors/{id}/measurements` returns 15-min periods;
   `/hours` is the mean of 4 of them (`coverage.observedCount = 4`). `/latest` returns the last
   15-min value, so it equals the hourly mean only by coincidence (5 of 58 sensors).
   → **`/latest` cannot be used as an hourly concentration.**
4. **Legacy + current sensors coexist.** ~310 CPCB stations list two sensors for the same parameter:
   a legacy series (e.g. sensor 35, 2016-02 → 2018-02) and the current series (e.g. 12234787,
   2025-02-18 → now). Choosing a sensor by parameter name is unsafe; pick the one with the newest
   sensor-level timestamp.
5. **Unit labels on the current CPCB series are unreliable.** no/no2/so2/co are labelled `ppb`:
   - CO "ppb" median 0.63, max 2.26 across 44 stations: implausible as ppb (ambient CO is
     hundreds of ppb); consistent with CPCB's mg/m³ (or ppm).
   - NOx "ppb" median 0.011 < NO2 median 12.8: impossible in the same unit; consistent with ppm.
   - NOx identity test (section 9): **24 stations fit NO/NO2 = µg/m³, 3 fit ppb, 14 ambiguous**
     on a single 15-min snapshot. The real unit differs by station.
   - O3, PM2.5, PM10 are labelled µg/m³ and have plausible magnitudes; no identity check possible.
6. **NH3 and Pb are not reported for India** (absent from the India parameter list). AQI will use
   at most 6 pollutants.
7. **Hour buckets are IST-aligned.** `/hours` periods run `HH:30Z → HH+1:30Z` (= IST whole hours).
   `/latest.datetime` and `period.datetimeTo` mark the **end** of the interval.
8. **`/days` window parameters are `date_from` / `date_to`.** `datetime_from` is silently ignored
   (returned 2025 rows for a 10-day request).
9. **`locality` is not usable as city** (6 of 642 monitors populated). CPCB names follow
   `"Site, City - AGENCY"` → deterministic parser + reviewed `city_mapping.csv`.
10. **Timezone** is `Asia/Kolkata` for all 764 locations.
11. **Rate-limit headers** present on every response: `x-ratelimit-limit` (60), `-used`, `-remaining`,
    `-reset` (seconds until the window resets). No 429 or retry was needed in 131 requests at 50/min.
12. **Backfill risk (Phase 7):** at R K Puram the current series starts 2025-02-18 and the legacy
    series stops 2018-02. Daily history for 2018–2025 may be sparse. Must be measured before the
    backfill estimate; `BACKFILL_START=2018-01-01` may be unrealistic.

## B. Hourly acquisition strategy

Measured cost basis: 466 fixed monitors active in the last 7 days × 5.8 live target sensors per
station ≈ **2,700 sensor series**. `/hours` exists only per sensor.

| Strategy | Requests / run | Correct hourly mean? | Late-data fill | Verdict |
|---|---:|---|---|---|
| A `/locations/{id}/latest` hourly | ~466 | **No** (15-min snapshot) | No | Rejected |
| B `/sensors/{id}/hours`, 3 h window, every sensor every hour | ~2,700 | Yes | Yes | Over budget (600) and over the 2,000/h hard limit |
| C `/parameters/{id}/latest` + India filter | n/a | No (15-min snapshot) | No | Filter unsupported |
| **D `/hours` in rotating cohorts** (proposed) | **~540** | Yes | Yes | **Fits budget** |

> **Phase 4 refinement (implemented):** cohorts are by `location_id % 6` with a **9-hour window**.
> Grouping by location keeps each station-hour row complete within one run. `% 5` put 629 live
> sensors in one cohort (over the 600 budget); `% 6` gives at most 485. Each station refreshes every 6 h.
> The original proposal is kept below for the record.

**Proposed: strategy D.** Split live sensors into 5 cohorts by `sensor_id % 5`. Each hourly run fetches
`/sensors/{id}/hours` for one cohort with an **8-hour trailing window** and upserts.
- Each sensor is refreshed every 5 h; the 8 h window overlaps the previous fetch by 3 h, so data that
  arrives up to ~3 h late is still captured. No duplicates: B returned 0 duplicate hours and the
  primary key makes re-fetches idempotent.
- Cost: ~2,700 / 5 ≈ 540 requests ≈ 11 min at 50/min. That fits the 600 budget and the 20-min Action timeout.
- Trade-off: a station's newest hour can be up to ~5 h + upstream lag old. Acceptable because AQI
  uses 24 h / 8 h averages. The dashboard shows "last observed" per station, so staleness is visible.
- The daily `sync_locations` job resolves the live sensor per (location, parameter) from sensor-level
  timestamps (finding 4).

Alternative if fresher data matters more than coverage: every sensor every hour with a 3 h window,
limited to ~100 stations (≈ 580 requests). **APPROVED 2026-09-28: strategy D.**

## C. Changes to project rules (approved 2026-09-28)

1. **Section 14.2 "round to UTC hour"** → store `reading_time = period.datetimeFrom` (UTC, `HH:30Z`)
   unchanged. Rounding would shift every value by 30 min and mislabel IST hours.
2. **Section 9.3 unit handling**: don't trust `ppb` labels on CPCB gas sensors. Classify each station's
   NO/NO2 convention from the NOx identity over 24–48 h of `/hours` (not one snapshot), commit the
   result as a reviewed `data/unit_convention.csv`, and convert accordingly. SO2 and CO follow the
   station's classified convention (flagged as an assumption). For unclassified stations, reject NO2/SO2/CO (logged) and compute AQI from PM2.5, PM10 and O3,
   which still meets the 3-pollutant rule.
3. **Section 9.1**: NH3 and Pb unavailable for India. Keep the breakpoint rows; they are simply never used.

  The CSV starts each next band at the next value at table precision (e.g. CO 10.1, Pb 0.6, PM10 431).
  Under the project's band rule (a value belongs to the first band with `C <= conc_high`),
  both readings put every concentration in the same band.
- The PDF names category 3 **"Moderately Polluted"**. The project uses "Moderate"; the dashboard may
  use either, but the README should mention the official name.
- The PDF gives a worked example to use as a unit test in Phase 3: PM2.5 sub-index = 51 at 31 µg/m³,
  100 at 60 µg/m³ and 75 at 45 µg/m³.

## E. City/state mapping evidence (Phase 2)

- Name suffix vs OpenAQ `owner` was tabulated for all 642 monitors. `AGENCY_STATE` in
  `src/city_mapping.py` only contains suffixes confirmed by an owner name (e.g. `MPCB` →
  "Maharashtra Pollution Control Board") or suffixes that name the state themselves ("Manipur PCB").
- Not trusted as state evidence: `WBSPCB` (one station's owner is "Bihar State Pollution Control
  Board", a metadata error), `APCB`, `SSPCB`, `ANPCC` (owners "Unknown"/"OpenAQ admin").
- National bodies (CPCB, IITM, IMD) take the state from other stations in the same city, and only
  if that city maps to exactly one state.
- Result: 628 of 642 monitors mapped to 286 city+state keys. Aurangabad correctly appears twice

## F. Gas unit classification results (Phase 2)

`python -m scripts.classify_units` over the 48 h ending at each station's last observation
(1,857 requests in two resumable passes, 0 retries). 472 stations have NO, NO2 and NOx sensors:

| Convention | Stations | Meaning for ingestion |
|---|---:|---|
| `ugm3` | 213 | NO2, SO2 µg/m³ as published; CO mg/m³ as published |
| `ppb` | 98 | NO2, SO2 converted ppb → µg/m³; CO treated as ppm → mg/m³ |
| `unclassified` | 161 | NO2/SO2/CO rejected (counted/logged). AQI from PM2.5, PM10, O3 |

Stations without NO/NO2/NOx sensors are also `unclassified` (the default).

**Tolerance choice (5%).** Of the stations with ≥ 12 matched hours, 222 of 361 in pass 1 had a
median ratio within **2%** of 1.0 for one hypothesis, which is a sharp cluster. Beyond that the
distance is spread out (2–5%: 28, 5–10%: 31, 10–20%: 49, > 20%: 31) rather than forming a second
cluster, so a wider tolerance would add stations where the identity doesn't hold rather than
near-misses. The two hypotheses differ by ×1.6–1.8, so they can never be confused either way.
Kept at 5%, favouring rejection over a wrong conversion.

By agency, DPCC (Delhi) is uniformly `ugm3` (24/24), while HSPCB, OSPCB and TNPCB are mostly
`ppb` or unclassified. The convention follows the reporting agency's data system, which supports
applying the station-level result to SO2 and CO (still flagged as an assumption).

## G. Historical backfill: `/days` behaviour (Phase 7)

Measured on the real endpoint while building `scripts/backfill_history.py`. Numbers marked *(partial)* come
from the first ~590-740 sensors fetched; the final-run numbers are added at the end of the phase.

**Response shape** (`/sensors/{id}/days`, checked on legacy sensor 1166 and current sensor 12234787).
Each result has `period`, `value`, `coverage`, `summary`, `parameter`, `flagInfo`, `coordinates`.
Day boundaries are local: `period.datetimeFrom.local` is `...T00:00:00+05:30`, so the IST date is its first
10 characters. `coverage` holds `expectedCount` (24), `observedCount`, `observedInterval`, `percentComplete`,
`percentCoverage`, and `datetimeFrom` / `datetimeTo` (first and last observation of that day).

**Two eras, almost nothing in between.** Legacy series cover 2018 to 2022-10-31; the current series starts in
February 2025. Only five metros (Delhi, Mumbai, Hyderabad, Kolkata, Chennai) have 2023-24 days (4,975 city-days).

**`observedCount` is not hours for the legacy series.**

| | current series | legacy series |
|---|---:|---:|
| sensor-days with `observedCount` above 24 | 0% | 61.8% (46.9% have 36 or more) |

`percentCoverage` only mirrors the count (34 observed of 24 expected shows 142%), so it carries no extra
information. The legacy series report sub-hourly or duplicate readings.

**Timestamps carry sub-hour offsets.** In the current series the first observation of a day falls at :45
(81% of 109,495 days), :15, :00 or :30. As a result N hourly readings span up to about 0.75 h less than N-1 hours:
the measured minimum span for 18 readings is 16.25 h (2,376 days).

**Completeness rule used by the backfill** (`station_day_values`): `observedCount >= MIN_HOURS_24H` and an
observation span of at least `MIN_HOURS_24H - 1 - 1` = 16 hours. On the first 586 sensors this rejects 0 of
93,383 count-passing current-era days and 7.7% of 178,299 count-passing legacy days *(partial)*. It cannot
see gaps inside the span. An earlier threshold of 17 h wrongly rejected 0.35% of current-era days; the
cache keeps the raw first/last timestamps, so the threshold can change without a re-fetch.

**Throughput.** `GET /days` took a median 1.74 s (0.85-3.62 s, 5 calls) and the Neon progress write 0.47 s, so
one worker manages about 17 requests/min against the 25/min throttle. Two or three workers run side by side
under a combined 35/min cap. Transient HTTP 500s occurred (2 in about 1,400 requests) and succeeded on retry.

**Agreement with the live pipeline.** For 209 current-era sensors at 37 stations against
`fact_pollutant_hourly` on 2026-09-23 and 09-24: where both sides had the same hour count (179
station-days) daily means differ by a median 0.07% (max 0.47%). The 161 pairs with different hour counts
differ more (median 0.74%) because the hourly table lacks the last hour of 09-24 (the seed ended at the feed
head). This confirms the IST-day alignment, the completeness rule and the unit handling.

**Upstream lag.** On 2026-10-02 06:03 UTC the newest R K Puram observation on OpenAQ was
2026-09-29T14:30Z (63.6 h old). `/days` holds complete station-days for 09-25 to 09-29 that the hourly table
never captured, because the 9-hour trailing window of the hourly strategy (section B) cannot recover a
multi-day upstream delay. The backfill fills those days in `daily_city_summary`; live rows still win.

**Operational.** An idle laptop slept for 45 minutes (30-minute AC timeout) and froze the run; `--fetch` now
holds a per-process Windows power request.

**Open: gas units at `ppb`-classified stations (see F).** Evidence so far, all from the hourly table, 16 cities
that have both conventions: SO2 relative to the NO2 control is higher at `ppb` stations by +0.77 on the log
scale (95% CI 0.24 to 1.28). The assumption predicts 0 and "SO2 is already ug/m3" predicts +0.96. CO shows no
such effect (-0.31, CI -0.56 to 0.00). Cross-era test on the full data (63 `ugm3` and 56 `ppb` cities):
current-converted over legacy-as-labelled, relative to PM2.5, is 1.07 / 1.15 / 1.08 (NO2 / SO2 / CO) at `ugm3`
cities and 2.04 / 3.04 / 1.17 at `ppb` cities. The `ppb`/`ugm3` gaps (1.9, 2.6, 1.1) equal the conversion factors
(1.88, 2.62, 1.15), so at `ppb` locations the legacy values (labelled ug/m3) are in the same unit as the current
raw values. For NO2 that unit is ppb (NOx identity), so the legacy NO2 label is wrong there. For SO2 and CO the
test cannot tell "ppb in both eras" from "ug/m3 in both eras". **Decision (owner, 2026-10-02):** at `ppb`
stations convert NO2 in both eras and exclude SO2 and CO in both eras until verified. Live ingest
(`src/units.py`) still applies the old SO2/CO assumption: separate follow-up.

**Final run.** 5,478 sensors in scope, 5,445 with data and 32 empty, about 4,860 requests in the final stage
(14 retries, 0 errors). Written to `daily_city_summary`: 210,523 `backfill` city-day rows in 286 cities
(268 further days were skipped because live rows exist), 0 duplicate keys, 296 live rows untouched; 1,036
city-days in 239 cities fill the live gap of 2026-09-25 to 09-29. Database 16 MB to 57 MB. Trend checks: median
PM2.5 winter 68.6, post-monsoon 57.4, summer 41.6, monsoon 24.9; Delhi April PM2.5 45.8 in 2020 against 78.8-79.9
in 2018, 2019 and 2021; Delhi PM2.5 peaks on Diwali day or the day after in 2018-2021, 2023 and 2025; in 2024 the peak came about three days later and the 2022 Diwali days are missing.
